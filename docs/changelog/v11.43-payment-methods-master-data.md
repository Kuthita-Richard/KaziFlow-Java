# v11.43 — Payment methods are master data (R1, step D) — release R1 "Trust" complete

## Before
Payment methods were a `CHECK(payment_method IN ('cash','mpesa','card','bank'))` on `sales` and five typed lists that disagreed with each other (sales: cash/mpesa/card/bank; purchases: + cheque, credit, "bank transfer"; expenses stored capitalised labels such as "Bank Transfer"; finance; fuel). Adding Airtel Money, a SACCO deduction or a voucher meant a schema migration.

## Bugs this found and fixed
- **M-Pesa at the till could not work.** The button's code was derived from its text (`"M-Pesa".toLowerCase()` = `"m-pesa"`), so the STK-push branch (`"mpesa".equals(selectedPayment)`) never ran, and a sale saved with `m-pesa` violated the `CHECK`. The till now selects the method's code.
- **The sales-history payment filter never matched M-Pesa**: it offered the label "M-Pesa" and compared it with the stored code `mpesa`.
- **The M-Pesa dialog pre-filled a sample phone number** (`0712345678`); an STK push goes to a real person. It now starts empty and requires a number.

## Added
- `payment_methods` master table (code, label, type, integration, active, order, used for: sales / purchases / expenses, system) with the six defaults; `services/PaymentMethods` (list by scope, `find`/`label` that also read the old free-text spellings — "M-Pesa", "bank transfer" — even after a rename, `isCash`, `isMpesa`, `add`, `update`, `setActive`); `utils/PaymentMethodCombo` (the one picker: value = code, display = label). A method has a **type** (cash gets the tendered/change row) and an optional **integration** ("mpesa" triggers the STK push), so behaviour no longer depends on button text. Methods are never deleted — switching one off stops it being offered but old documents still show it; `cash` (the default of a sale and of a refund) cannot be switched off.
- **Settings → Payment Methods**: add, edit (name, position, where it is used) and switch on/off; problems are shown and the dialog stays open. Changes are audit-logged.
- The till, sales history (filter and badges), purchases, expenses and finance now read the list.

## The migration (`database/PaymentMethodMigration`, run by `SchemaMigrations`)
SQLite cannot drop a CHECK, so `sales` is rebuilt (CHECK replaced by `REFERENCES payment_methods(code)`): consistent backup first (`VACUUM INTO …pre-paymentmethods-<time>.bak` next to the database; no backup, no migration); foreign keys OFF for the rebuild (ON would cascade-delete `sale_items`) and back ON in a `finally`; the new table is derived from the CURRENT stored definition so columns added later are kept, and the column lists are compared; one `BEGIN IMMEDIATE` transaction with the row count and the sum of totals verified after the copy, indexes/triggers/views recreated, the AUTOINCREMENT counter preserved, and no MORE foreign-key violations than before (a legacy database may already contain orphans). Any failure rolls back and the old table keeps working with its four methods; until the upgrade has run, custom methods can be added for purchases and expenses but not for sales (with a clear message). Idempotent; runs in standalone, server and shared-file modes, not in LAN client mode.

## Verified
`tools/checks/PaymentMigrationCheck` (24 assertions; mutation-tested 8/8) on a COPY of a populated pre-migration database (`tools/checks/fixtures/legacy-v11.42-populated.db`: 40 sales across the four methods, 79 sale lines, eTIMS serials, a return, purchases, quotations, the demo company): row counts identical in 17 business tables, children still join, columns/indexes identical, integrity and foreign keys clean, the backup is the legacy snapshot, running again changes nothing, and failure injection (temp name taken → rollback and foreign keys restored; a method in use missing from the master table → stopped before anything is touched; a pre-existing orphan → still migrated; views, triggers and an AUTOINCREMENT counter ahead of the highest id → preserved). `tools/checks/PaymentMethodsCheck` (36 assertions; mutation-tested 10/10): defaults and scopes, every stored spelling, add/update/switch-off rules, the pickers, saving a sale with every method (including one added in Settings; an unknown code is refused), the till (button list, the `mpesa` code, the cash row), the history filter and badges, and the Settings dialog. `TrustGuardTest` +4 phrases (typed payment lists). Full regression: 24 suites, 0 failures; JUnit 240 tests, the same 25 pre-existing failures.
