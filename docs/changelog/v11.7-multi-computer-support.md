# v11.7 — Multi-Computer Support (Phase 10D)

**Design decision:** both modes are implemented, selectable at setup time in Settings → Network / Multi-Computer, per your instruction to let the user choose rather than picking one for them:
1. **Shared Database File** — every PC points at one SQLite file on a network share. Simplest to set up, but comes with an explicit warning: SQLite isn't designed for concurrent writes from multiple PCs over a network file share, even with WAL mode — risk of corruption with several tills writing at once.
2. **Server / Client** — one PC hosts, others connect over the LAN. More code, but the only mode that's actually safe for concurrent multi-till POS use, since each client gets its own dedicated connection session on the host with correct transaction semantics.

## A big compilation breakthrough this session
Discovered this sandbox has **no Maven Central access** (confirmed via direct test — `403 host_not_allowed`) and **no local JavaFX/dependency cache**, meaning nothing in this project had been verified to actually compile since work began (v9 onward) — only manually reviewed. Installed a real JDK via `apt-get install openjdk-21-jdk-headless` (Ubuntu's archive mirrors *are* reachable), which unlocked `javac` for the first time. Everything in this package uses only the JDK's built-in `java.sql`/`javax.net.ssl`/etc. — **no external Maven dependency at all** — so it was possible to compile and, further, to actually runtime-test this feature for real, which is documented below.

## New package: `com.kaziflow.network`
- **`NetProtocol.java`** — wire format for LAN server mode. A client-side `PreparedStatement` buffers every `setX()` call locally and sends exactly **one** request when `execute()` is finally called (SQL + all params together) — the server never sees a multi-step prepare/bind/execute conversation, only "run this SQL with these params."
- **`MiniJson.java`** — a small hand-written JSON encoder/decoder built specifically for this protocol. Originally used Gson (already a project dependency), but Gson isn't published as a standalone jar via GitHub Releases either (source-only, relies on Maven Central for distribution) — same reasoning as `EmailService`'s dependency-free raw-SMTP approach in v11.3. Round-trip tested at runtime with tricky cases (embedded quotes, newlines, tabs, backslashes, nulls) — all correct.
- **`NetworkConfig.java`** — multi-computer mode setting, stored in a flat `~/KaziFlowERP/network.properties` file rather than the `settings` DB table. This is deliberate: in CLIENT mode there's no local database to query yet — `DatabaseManager.getConnection()` needs to know "go connect to another PC" *before* it can do anything DB-shaped. Reading that from a DB row would be a chicken-and-egg problem; a flat file sidesteps it.
- **`NetworkServer.java`** — the host side. Each accepted client connection gets **one dedicated real JDBC `Connection`** to the local SQLite file, held for that session's lifetime — this is what preserves transaction correctness for multi-statement operations like `Sale.save()` (`setAutoCommit(false)` → insert sale → insert sale_items → `commit()`).
- **`RemoteConnection.java`, `RemoteStatement.java`, `RemotePreparedStatement.java`, `RemoteResultSet.java`, `RemoteResultSetMetaData.java`** — client-side implementations of `java.sql.Connection`/`Statement`/`PreparedStatement`/`ResultSet`/`ResultSetMetaData`. Scoped precisely: every JDBC method actually called across all 26 DAOs was enumerated first (by grep) before writing these, so only that exact surface is implemented; everything else throws a clearly-labeled `UnsupportedOperationException` rather than silently doing the wrong thing.
- **Zero changes needed to any existing DAO.** Every one of them calls `DatabaseManager.getInstance().getConnection()` exactly as before — it has no idea whether it got back a local SQLite connection or a `RemoteConnection` proxying to another PC.

## `DatabaseManager` changes
- **Where:** `src/main/java/com/kaziflow/database/DatabaseManager.java`
- `getConnection()` is now mode-aware: `STANDALONE`/`SERVER` → real local file; `SHARED` → a configurable network file path instead of the default; `CLIENT` → a new `RemoteConnection`.
- New `getLocalConnection()` — **always** the true local file regardless of mode, used exclusively by `NetworkServer` so a host machine can never accidentally proxy to itself or elsewhere.

## Settings UI
- **Where:** `src/main/java/com/kaziflow/views/SettingsView.java`, `src/main/java/com/kaziflow/App.java`
- New "Network / Multi-Computer" card → radio-button choice of the 4 modes, with mode-specific fields (server: port; client: host/port + a live **Test Connection** button; shared: file path + the concurrency warning above).
- `App.java` starts `NetworkServer` automatically at launch if configured for `SERVER` mode.

## Real runtime verification (not just static review)
Since a real `javac` became available, this was tested end-to-end against an **actual SQLite database** downloaded as a genuine jar from `xerial/sqlite-jdbc`'s GitHub Releases (GitHub Releases do publish real binary jars for this project, unlike Gson) — not just read for correctness:
- ✅ Real socket connection, `PING` round-trip
- ✅ `INSERT ... RETURNING generated key`, fetched back correctly on the client
- ✅ Query round-trip (`SELECT ... WHERE id = ?`) returns correct data
- ✅ **Transaction test** mirroring `Sale.save()`'s exact pattern: `setAutoCommit(false)` → insert parent row → insert child row → `commit()` — verified visible from a completely separate direct local connection afterward
- ✅ **Rollback test** — verified the row genuinely does not exist afterward
- ✅ NULL parameters via both `setNull()` and `setObject(i, null)` — round-trip correctly, `wasNull()` reports correctly
- ✅ Real SQL errors (querying a nonexistent table) propagate as a genuine `SQLException` with the underlying SQLite error message intact, and the connection **remains usable afterward** — a corrupted session after one bad query would be a serious problem for a long-lived POS shift

One real bug was caught and fixed *during* this process purely because a real compiler was available — several missing `ResultSet`/`PreparedStatement` interface method overrides (`updateCharacterStream` long-length variant, `getHoldability`, `updateBigDecimal`, `setNull(int,int,String)`, others) that static review alone would not have caught, since Java's compile-time "must implement every abstract method" check is exactly the kind of thing that requires an actual compiler to verify.
