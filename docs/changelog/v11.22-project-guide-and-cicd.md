Three deliverables, all requested directly.

## 1. `docs/PROJECT_GUIDE.md` — onboarding doc for future developers and AI agents

Requested specifically so that (a) future developers don't reconstruct months of context from scratch, and (b) other AI agents can be brought in productively — the project owner plans to run multiple assistant-developer accounts in parallel (~2 months out) with this project's owner acting as validating administrator.

## 2. Real-world reference material analysis (§8 of the guide)

The project owner shared a real Kenyan healthcare group's internal memo plus 47 screenshots of a live production HMIS (46 distinct modules), and a catalogue of those modules. Analyzed for **architectural intent**, not as a feature checklist. Key findings now documented:

- **Multi-payer, multi-branch pricing is the single biggest structural gap.** The reference prices every item differently by payer type (cash/insurance scheme/corporate) *and* branch; the real memo independently names nine actual Kenyan insurance schemes that daily reporting must break down by. KaziFlow has one flat price per product and no payer-type concept at all.
- **Confirm→Reverse / Draft→Finalize is the correct financial pattern** — real systems reverse rather than delete, and the reference has genuine double-entry infrastructure (General Journal, real Chart of Accounts, Opening Balances, Trial Balance) that KaziFlow still lacks even after v11.19/v11.20 removed the fabricated figures.
- **Self-service is a permissions layer over shared data, not duplicated screens** — concrete confirmation for how to approach the requested dynamic-roles work.
- **One inventory engine serving many verticals** — confirms KaziFlow's existing shared `ProductDAO`/`StockTakeDAO` approach is already pointed the right way.
- **Compliance/reporting formats should be country-swappable**, not just the rates within them.

The reference catalogue itself is preserved at `docs/reference/HMIS_Feature_Reference.md`.

## 3. CI/CD — `.github/workflows/`

**`ci.yml`** — compiles and runs the existing 11 test files on every push/PR, on a GitHub-hosted runner with full Maven Central access. This directly addresses the most persistent problem of this whole project: the development sandbox cannot compile JavaFX code, so **every real compile error this session was found by the project owner running `mvn javafx:run` manually** (a `Dialog<Void>` that should have been `Dialog<ButtonType>`, a missing `List`/`ArrayList` import, a variable accidentally deleted mid-edit). All three would have been caught automatically here.

**`release.yml`** — matrix build producing native installers for Windows/macOS/Linux on a version tag push. This solves a real, documented constraint: `jpackage` cannot cross-compile, which is why three separate installer scripts exist and why shipping all three previously required physical access to all three machines.

Deliberately, `release.yml` **calls the existing `installer/build-*.sh|bat` scripts rather than reimplementing their jpackage commands inline.** A first draft did inline them, then reviewing the actual scripts showed they do meaningfully more than a naive inline version — notably a `jlink` step producing a trimmed custom runtime so end users don't need a JDK installed, plus icons, license file, menu/shortcut registration and app metadata. Duplicating that would have guaranteed drift the first time either copy was edited — the same DRY principle that motivated `DialogUtils` in v11.21.

Both workflows validated as parsable YAML, all three referenced scripts confirmed present, and the jar filename the Linux script hardcodes (`kaziflow-erp-1.0.0-fat.jar`) verified against what the shade plugin actually produces from `pom.xml`.
