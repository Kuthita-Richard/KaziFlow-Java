# v11.17 — Purchases Inflated Stock on "Pending" Orders — Fixed by Completing an Already-Designed Workflow

## The bug

- **Where:** `src/main/java/com/kaziflow/dao/PurchaseDAO.java`, `src/main/java/com/kaziflow/views/PurchasesView.java`
- The purchases table schema was already designed for a pending → received workflow: `status TEXT DEFAULT 'pending' CHECK(status IN ('pending','received','partial'))` plus a `received_by` column to record who confirmed receipt. But `PurchaseDAO.save()` called `addStock()` **unconditionally**, regardless of status — meaning creating a purchase order (the button is literally labeled "Create Purchase Order," and the code explicitly sets `status = "pending"`) immediately inflated on-hand stock as if the goods had already arrived.
- **Real consequence:** stock shown as available before it physically exists in the shop — risk of overselling at the POS, and inaccurate stock valuation reports, for every single purchase order created in the app's history (this is pre-existing, not introduced this session).
- Confirmed via grep that `AddPurchaseDialog.java`, `NewPurchaseView.java`, and `PurchaseOrderView.java` (three other purchase-related view files with more complete status handling) are never referenced from anywhere and are dead/unreachable code — the live path is entirely inside `PurchasesView.java`.

## The fix — completing the workflow the schema already anticipated

- `PurchaseDAO.save()` now only adds stock immediately if the purchase is created already marked `"received"`. Otherwise it stays pending, with no stock added, until receipt is confirmed.
- New `PurchaseDAO.markReceived(purchaseId, receivedByUserId)` — adds stock for every line item and records `received_by`, guarded with `WHERE status != 'received'` so it can never be applied twice (a double-click or accidental repeat call is a safe no-op, not a double-credit of stock).
- New **"📥 Receive"** button in the purchases table, shown only for orders not already received. Confirms with the cashier before applying ("this adds all its items to stock — only do this once the goods have actually arrived").

## Worth knowing: this adds a step to every purchase

Before this fix, every purchase updated stock in one click, correctly or not. Now, since `PurchasesView`'s "New Purchase Order" dialog always creates purchases as `"pending"`, **every purchase — including a same-day cash-and-carry purchase where goods are already in hand — now needs an explicit second "Receive" click** before stock reflects it. That's the correct trade for genuine purchase orders (goods ordered but not yet arrived), but it is real added friction for the common case of walking into a wholesaler and buying stock outright. Didn't unilaterally decide this either way (e.g., by adding a "received immediately" checkbox at creation time to skip the extra step for cash purchases) — that's a real product/workflow decision, not something to guess at silently.
