# v11.42 — Document numbers (R1, step C), the SQLite driver, and more demo data found

## ⚠ The pinned SQLite driver cannot read back a new row id
`pom.xml` pinned `sqlite-jdbc` **3.44.1.0**. In that release (and 3.43.x) `Statement.getGeneratedKeys()` is not implemented and throws `SQLFeatureNotSupportedException`; 3.42.0.0 and 3.45+ implement it. Verified here against the official 3.44.1.0 jar, Ubuntu's source build of 3.44.1.0, and 3.42.0.0 / 3.43.2.2 / 3.45.1.0 / 3.46.1.0. About 26 call sites depend on it (`SaleDAO.save` = checkout, `PurchaseDAO`, `QuotationDAO`, the vertical DAOs, …), and `SaleDAO.save` has no guard: with the 3.44.1.0 driver every checkout failed and returned null.
- The pom now pins **3.46.1.0**. **Please confirm on your Windows build (`mvn javafx:run`): complete a sale.** If checkout already worked for you on 3.44.1.0 something else is different in your environment, and the bump is harmless; if it did not, this was the cause.
- The earlier verification never exercised these paths (no suite saved a sale through `SaleDAO`), so this had been invisible. `NumberSequenceCheck` now does.

## Added: `services/NumberSequence`
One atomic, gapless, configurable sequence per document type (`DocType`: sales invoice, purchase order, quotation, sales return, stock transfer, employee, local eTIMS serial). It replaces `SELECT COUNT(*)+1` in `SaleDAO`, `PurchaseDAO`, `QuotationDAO`, `SaleReturnDAO`, `BranchDAO` (transfers), `EmployeeDAO` and `ETIMSService` (`MAX(sequence)+1`).
- The count approach gave two cashiers the same number, failed with `SQLITE_BUSY_SNAPSHOT` when another writer committed between the read and the write, and collided after any delete (the count dropped to a number that already existed; the UNIQUE insert then failed at checkout).
- `NumberSequence.next(conn, type)` is called on the connection of the transaction that stores the document, and its **first statement is a write** (the transaction takes the write lock before it reads anything). If the transaction rolls back the counter rolls back too, so numbers have no gaps (tax invoices). A first use on a database that already has documents continues after the highest existing number. Prefix and padding live in `number_sequences` (`configure`); `peek` shows the next number without using it (the purchase form preview, and the M-Pesa reference, which used to be `INV-<orders today>` — "INV-3" on the customer's phone and the same every day).
- Checkout (`SaleDAO.save`) retries the whole transaction on a busy database (3 attempts); a failed sale no longer burns its number. `ETIMSService.generateSerial` allocates its counter the same way and retries (it was a read-then-write that could duplicate a sequence).
- Lesson recorded in the code: even `CREATE TABLE IF NOT EXISTS` on an existing table starts a read snapshot, which is why the table is created at start-up and the allocator never runs DDL first.

## Added: `database/SchemaMigrations.runAll()`
The block of `ensureTables()` / column migrations that lived in `App.start()` is now one callable method (App and the checks both call it). A database that went only through `DatabaseManager.initialize()` used to lack `sales.delivery_charge`, the audit-log hash columns (`[AuditLog] Failed to write: no such column: record_hash`) and every optional-module table. This closes the v11.35 AuditLog finding.

## Demo / invented data removed (same rule as v11.37)
- `CustomerDAO.seedIfEmpty()` inserted 5 demo customers at every start **and every time the Customers tab was opened with an empty table** (it came back after you deleted them). Gone; customers are part of the opt-in `DemoDataService` now (49 rows in total).
- `EmployeesView` showed **invented leave requests** (John Doe, "Family vacation", 2024 dates) whenever the real list was empty. Gone.
- Customers tab: "Repeat Buyers" was `customers − 2`; it is now the number of customers with two or more completed sales. "Walk-in Sales" was a permanent "—"; it is now the count of completed sales with no customer.

## Verified
`tools/checks/NumberSequenceCheck` (27 assertions; mutation-tested 8/8 including the exact old `COUNT(*)+1` checkout, a read-first allocator, and an allocator outside the transaction): fresh start, rollback returns the number, continues after existing documents, format change, 8 threads × 20 raw allocations (unique and exactly 1..160), **8 cashiers saving 48 sales through the real `SaleDAO`** (none lost, 48 distinct consecutive invoices), a failed sale does not consume its number, saving after a delete does not collide, the previewed purchase number is the one saved, quotations and employees, and the eTIMS serials under the same load (all present, no duplicates). `InventedFiguresCheck` (customers tab, 38), `PeopleFiguresCheck` (no invented leave rows, 20), `DemoCompanyCheck` (customers, 20), `TrustGuardTest` +9 phrases (including every `…-%04d` format). The JUnit test that required `PurchaseDAO` to keep a private count-based `generatePurchaseNumber(Connection)` guarded the old design; it now asserts the opposite. Full regression: 22 suites, 0 failures; JUnit 240 tests, the same 25 pre-existing failures.
