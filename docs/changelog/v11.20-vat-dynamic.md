# v11.20 — VAT Made Genuinely Dynamic Project-Wide (Not Just Configurable-Looking)

**Context:** explicit request that statutory rates — starting with VAT — be genuinely dynamic (read from the database), not hardcoded, as a standing principle for how this app should be built going forward.

**Note:** this exact set of changes was implemented once, lost to a sandbox reset before it could be saved to outputs, and redone from memory in the same session. Verified balanced across every touched file after redoing it.

## What was actually found

Settings → Tax Settings already had a working "VAT Rate (%)" field that saved to `settings.vat_rate`, with UI text literally claiming *"Changing this affects all new receipts."* Checked whether that was true: only `ReceiptPrinter` (receipt display text) ever read the value back. Every real calculation — the actual POS checkout in `SalesView`, quotations, restaurant orders, three report/export paths — hardcoded `0.16` directly. Changing the setting did nothing to real totals. Same "config UI that promises dynamic behavior but nothing consults the underlying value" pattern already found and fixed for Branch Management (v11.15) and Payroll Tax (v11.18).

## New: `VATConfig`

Same pattern as `PayrollTaxConfig`/`CurrencyService` — singleton, reads from `settings` (`vat_rate`, plus a new `vat_enabled` toggle for a business that isn't VAT-registered), `getRate()` returns the decimal multiplier every calculation site actually needs. Settings → Tax Settings now calls `VATConfig.reload()` on save, so a rate change takes effect immediately, no restart needed.

## Every real hardcode found and fixed (10 sites, swept twice — once for `0.16`, once for the `1.16` multiplier form which the first sweep would have missed)

- `SalesView.java` — the actual POS checkout math (×2), plus the loyalty-redemption cap calculation which used the `1.16` form
- `QuotationDAO.java`, `QuotationView.java`, `RestaurantDAO.java` — one each
- `ReportExportService.java` — the Finance Summary CSV export, which had the *exact same* double-counting **and** wrong-basis bug already fixed in FinanceView (v11.19): VAT-on-VAT-inclusive-revenue, and "input VAT" computed from general expenses instead of actual purchases
- `FinanceView.java` — a **4th** instance of that same bug, found in the 6-month VAT history chart. Fixed with two new `TransactionDAO` methods, `getOutputVATForMonth()`/`getInputVATForMonth()`, mirroring the already-existing `getRevenueForMonth()`/`getExpensesForMonth()` pattern exactly.
- `ReceiptPrinter.java` — realigned to read through `VATConfig` instead of parsing `vat_rate` inline, so it also respects the new VAT-enabled toggle and there's exactly one source of truth
- `AddPurchaseDialog.java`, `NewPurchaseView.java`, `PurchaseOrderView.java` (×2 each) — the three confirmed-dead/unreachable purchase view files (see v11.17's notes) still had the hardcode. Fixed anyway for consistency — leaving known hardcodes lying around contradicts the "dynamic everywhere" principle even in dormant code paths.

## Still using a fixed default (not yet made dynamic, flagged for a future pass if wanted)

The loyalty points earn-rate in `SalesView.applyLoyaltyForCompletedSale()` is hardcoded as "1 point per KES 100 spent." Same category of thing as VAT/payroll rates — a business-specific number baked into code instead of configurable. Not fixed in this pass since it wasn't part of what was asked, but noted here as a natural next candidate under the same "make it dynamic" principle.
