# v11.9 — Functional Recheck: Checkout Interactions, Customer Naming, Currency/Receipt Consistency

Requested: re-verify functionality, not just compile correctness. This pass specifically targeted places where multiple v11.x features interact — numpad + loyalty + delivery all touch the same totals logic in `SalesView`, and multi-currency touches every money label across the app. Interaction bugs hide even when every individual feature compiles and works in isolation.

## Real bug fixed: customer name recovered by fragile regex

- **Where:** `src/main/java/com/kaziflow/views/SalesView.java`
- **Problem:** `completeSale()` recovered the plain customer name by regex-stripping `" (phone)"` off the combo box's display label (`customerCombo.getValue().replaceAll(" \\([^)]*\\)$", "")`). This breaks for any customer whose real name itself contains parentheses (e.g. "John (Junior) Mwangi") — the regex would strip part of their actual name.
- **Fix:** Added a proper `customerLabelToPlainName` map, populated directly from the DB alongside the existing id map in `refreshCustomerCombo()`. The plain name is captured once, correctly, at selection time (`customerCombo.setOnAction`) into a new `selectedCustomerName` field, and `completeSale()` now uses that field directly — no string parsing involved at all.

## Real inconsistency fixed: loyalty redemption cap disagreed with itself

- **Where:** `src/main/java/com/kaziflow/views/SalesView.java`, `showRedeemPointsDialog()`
- **Problem:** The redemption dialog capped requested points against `currentTotal`, which includes the delivery charge. But `updateTotals()`'s own safety net (added in v11.6 alongside delivery) re-caps `redeemedDiscount` against goods-only total (subtotal + VAT, excluding delivery) immediately afterward. The two caps disagreed — the dialog implied points could discount delivery too, then a silent second correction one line later meant they never actually could.
- **Practical impact:** Not a crash or data-corruption risk — `updateTotals()` always ran immediately after and self-corrected before anything was displayed or saved, and the confirmation toast (built from the fields *after* that correction ran) always showed the truthful final number. But the dialog's own cap was functionally dead code, silently overridden a line later, which is fragile and confusing to reason about even though it happened to be safe.
- **Fix:** The redemption dialog now caps against the same goods-only total (`subtotal × 1.16`) that `updateTotals()` uses, so both caps agree from the start. This also makes explicit, as a real business rule rather than an accident: **loyalty points discount goods, not delivery charges** — consistent with how most real loyalty programs work.

## Verified correct via hand-simulation: SACCO loan amortization

Simulated `disburseLoan()`'s exact reducing-balance formula independently (principal=12,000, annual rate=12%, 12-month term) and walked all 12 installments by hand. Confirmed:
- Total principal repaid across all installments exactly equals the original principal (12,000.00)
- Final remaining balance after installment 12 is exactly 0.00
- Every installment's total (principal + interest) is a consistent, correctly-declining amortization — matches a standard bank/SACCO EMI schedule

## Verified correct: currency conversion direction

Multi-currency's exchange-rate math (`CurrencyService`) and the Settings dialog's "KES per 1 USD" input were traced through by hand for a round trip: entering 130 (KES per USD) → stored internally as `1/130` (USD per KES, matching the field's own documented convention) → displaying 1,300 KES converts to exactly 10 USD. No inversion bug — this is a place currency code very commonly gets the direction backwards, so it was worth explicitly confirming rather than assuming.

## Deliberately left unchanged: receipts still always show KES, even in USD/EUR display mode

- **Where:** `src/main/java/com/kaziflow/services/ReceiptPrinter.java`
- This looks like the same "hardcoded KES" pattern fixed in `KESFormatter`/`SalesView` back in v11.3, and my first instinct was to "fix" it the same way — **that would have been wrong.** Receipts are tied to `ETIMSService` (Kenya's KRA electronic tax invoicing system), which requires amounts in KES specifically. All amounts are stored in KES internally regardless of display currency (see v11.3's design decision) — a receipt showing a USD-converted figure using a business-editable exchange rate would be a real compliance problem, since it's a legal record of the actual transaction, not a convenience dashboard view.
- **Decision:** Receipts (print, WhatsApp, SMS, email) intentionally continue to always display KES. Dashboard/UI screens correctly use the currency-aware formatter since those are for the business owner's convenience, not tax records. This distinction is now documented here explicitly so a future pass doesn't "fix" this the wrong way.
