# v11.4 — Hash-Chained (Tamper-Evident) Audit Trail

**Task:** Security hardening request — "chain-linking through cryptography and hashing, a blockchain-like application of the concept, but not literally a blockchain."

## What changed
- **Where:** `src/main/java/com/kaziflow/services/AuditLog.java`, `src/main/java/com/kaziflow/views/SettingsView.java`, `src/main/java/com/kaziflow/App.java`
- Every `audit_log` row now stores `prev_hash` and `record_hash`, where `record_hash = SHA-256(prev_hash + user_id + user_name + action + description + module + record_id + timestamp)`.
- Because each row's hash depends on the row before it, editing or deleting any historical row breaks every hash that comes after it in the chain — this is deliberately *not* a real blockchain (no consensus, no mining, no distributed nodes needed for a single local database), just the tamper-evidence property borrowed from the same idea.
- `ensureHashColumns()` — idempotent `ALTER TABLE` migration, registered at startup.
- `verifyChainIntegrity()` — walks the whole table in insertion order, recomputes each row's hash from its own stored fields + the previous row's stored hash, and reports exactly which row(s) broke and how, if any did.
- New **"🔗 Verify Chain Integrity"** button in Settings → Audit Trail.

## Real concurrency bug found and fixed while building this
- **Problem:** The old logger fired every write on its own unordered `new Thread(...).start()`. Two near-simultaneous `AuditLog.log()` calls could race to read "the last hash," both compute a hash chained from the same parent, and silently fork the chain — which is invalid by construction for a hash chain.
- **Fix:** Writes are now serialized through a single-thread `ExecutorService` (`audit-log-writer`), so hashes are always computed and inserted strictly one at a time. No functional behavior changed from the caller's side — `AuditLog.log(...)` is still fire-and-forget.
