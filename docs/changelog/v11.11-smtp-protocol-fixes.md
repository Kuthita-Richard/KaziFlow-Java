# v11.11 — SMTP Protocol Bugs (dot-stuffing, CRLF injection) + Full-Project Misnesting Sweep

## Sweep for the v11.10 bug class across the whole project

Wrote a proper depth-tracking script (not just brace counting) to check every `if (var.equals(...))` dispatch chain in the entire codebase for the same "swallowed by an unclosed sibling" pattern found in `SettingsView.java`. Checked every file — **no further instances found**. Also checked all old-style colon-`switch` statements in the project for fallthrough risk; the two files I touched this session (`CalculatorDialog.java`, `QuotationView.java`) both use modern arrow-`switch` (`case X ->`), which has no fallthrough risk by design.

## Real bug: missing SMTP dot-stuffing (RFC 5321 §4.5.2)

- **Where:** `src/main/java/com/kaziflow/services/EmailService.java`
- **Problem:** The SMTP `DATA` command's message body is terminated by a line containing only a single `.`. Per RFC 5321, any line *within* the message that itself starts with a literal `.` must have it doubled (dot-stuffing), or a compliant SMTP server reads that line as the end-of-message marker and silently truncates everything after it. This wasn't implemented at all. Receipts are line-based formatted text (separators, amounts) — a genuinely reachable case, not a theoretical one.
- **Fix:** Added dot-stuffing to every line of the body before sending. Verified with a standalone runtime test covering: a line that's exactly `.`, a line starting with `.` followed by text, and a normal multi-line body — all transform correctly (confirmed via `javac`/`java`, not just read).

## Real bug: no defense against SMTP/header injection via pasted input

- **Where:** same file, `send()`
- **Problem:** The recipient email address (entered via a free-text dialog when sending a receipt) is placed directly onto its own line in the SMTP protocol (`RCPT TO:<...>`) and in the `To:` header. A pasted CR or LF character in that field could inject additional SMTP commands or extra email headers. Low practical severity here (this requires the *cashier* pasting malicious text, not an external attacker), but a real, unguarded gap for a feature that accepts free-text input and drops it straight into a hand-rolled protocol.
- **Fix:** `send()` now rejects any recipient or subject containing a `\r` or `\n` before doing anything else, with a clear error message. The message body is unaffected (it's meant to contain newlines, and dot-stuffing above already makes its transmission safe).

## Minor: misleading startup log

- **Where:** `src/main/java/com/kaziflow/database/DatabaseManager.java`
- The startup log always printed the hardcoded local database path, even in `SHARED` or `CLIENT` network mode where that's not actually where the data lives — actively misleading if you were troubleshooting a multi-computer setup. Now reports the real mode and actual location (local path / shared file path / remote server address, as appropriate).
