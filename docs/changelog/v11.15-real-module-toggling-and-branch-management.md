# v11.15 — Real Module Enable/Disable Feature Built; Branch Management Fixed

Triggered by a user question about running a multi-vertical business (pharmacy + clinic + nursing home + multiple branches under one company) on the CUSTOM profile. Answering that properly required checking whether the tools to actually do it existed — they didn't, in two separate ways.

## Found: two more real, pre-existing bugs

**1. `ModuleRegistry`'s "enable/disable individual modules" was documented but never built.**
- The class's own Javadoc listed this as a responsibility ("Handles enable/disable of individual modules at runtime"). The Settings → "System Modules" card's description said the same ("Enable/Disable Inventory, POS, HR, or Workshop modules"). Neither was backed by any actual code — no method anywhere in `ModuleRegistry` did this.

**2. The "System Modules" card's click handler opened the wrong feature entirely.**
- **Where:** `src/main/java/com/kaziflow/views/SettingsView.java`
- Clicking "System Modules" actually opened `BranchView` (branch/location management) — a completely different, mislabeled feature. Meanwhile `BranchDAO`/`BranchView` themselves are fully built and working (location tracking, inter-branch stock transfers) but had no dedicated, correctly-labeled entry point anywhere.

## Fixes

**Real module toggling, built from scratch — `ModuleRegistry.java`:**
- `loadModules()` now checks for a saved override list first, falling back to the active profile's default list only if none exists.
- New `settings` table key `module_overrides` (comma-separated module ids) persists a manual selection independent of whatever `IndustryProfile` is active.
- New API: `getAllAvailableModules()`, `getEnabledModuleIds()`, `hasModuleOverrides()`, `setModuleOverrides(Set)`, `clearModuleOverrides()`.
- `setProfile()` now clears any existing override when switching profiles — otherwise a stale override would silently make profile-switching appear to do nothing.

**Real toggle UI — `SettingsView.showModuleTogglesDialog()`:**
- A checklist of every module the app knows about, pre-checked to reflect whatever's actually active right now (override or profile default). Dashboard/Settings/Help are locked on and can't be unchecked — turning them off would strand the user with no way back into Settings to undo it.
- "Save" persists the selection and immediately rebuilds the sidebar (`SceneManager.showMainApp()`) — verified this actually works by checking `MainLayout`'s constructor reads `ModuleRegistry.getInstance()` fresh every time, and `showMainApp()` creates a brand-new `MainLayout` on every call. Not assumed — traced the whole chain.
- "Reset to Profile Defaults" discards the override and reverts to the active profile's plain list.

**Branch Management given its own real entry point:**
- New "🏢 Branch Management" card added to Settings, correctly wired to `new BranchView().show()` — the feature that was already fully built and now has a genuine way to reach it.
- "System Modules" now correctly opens the new toggle dialog described above.

**Bonus fix found while touching this area — settings grid layout was fragile:**
- **Where:** same file, `buildModuleGrid()` (or equivalent)
- The settings cards were distributed into 3 hardcoded, non-wrapping `HBox` rows (first 4 → row 1, next 3 → row 2, everything else → row 3, regardless of actual count). This was already imbalanced before this session and would only get worse as more cards get added — row 3 would just keep growing wider with no wrapping, risking overflow off-screen. Replaced with a `FlowPane`, which wraps automatically to fit available width no matter how many cards exist — robust to future additions without needing to manually rebalance row splits again.

## Answering the original question

With this now genuinely working: for a business spanning pharmacy + clinic + nursing home + multiple branches, the intended path is — pick **CUSTOM** as the Industry Profile, use the new **System Modules** screen to turn on the union of what's needed (Inventory, Batch/Expiry for drugs, Sales & POS, Purchases, Patients, Appointments, HR, Finance, Reports, Branch Management for the multiple locations), and use **Branch Management** to track each physical location and transfer stock between them. Worth being upfront about a real limitation: this app has **one shared module set per installation**, not per-branch — every branch sees the same active modules; there's no way to make Branch A pharmacy-only and Branch B nursing-home-only within one installation. For that kind of true operational separation, running separate installations per branch (each with LAN-server/shared-DB pointed at branch-specific needs) would be the more accurate fit, not this single-database multi-module approach.
