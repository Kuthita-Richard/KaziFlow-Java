# v11.12 — Foreign Key Enforcement Was Silently Off Everywhere (Pre-Existing, Definitively Proven and Fixed)

This is the most significant finding of the "check everything" pass so far, in terms of scope of impact.

## The bug

- **Where:** `src/main/java/com/kaziflow/database/DatabaseManager.java`
- SQLite has `PRAGMA foreign_keys = ON` as a **per-connection** setting — it is NOT persisted in the database file itself (unlike `journal_mode = WAL`, which IS a database-level setting that sticks once set). `initialize()` sets `foreign_keys = ON` on the one connection it uses for schema setup at startup, then that connection closes.
- Every DAO in this codebase (26+ of them) opens a **brand-new connection per call** — there's no connection pooling — via `DatabaseManager.getInstance().getConnection()` / `getLocalConnection()`, which was just a raw `DriverManager.getConnection(...)` with no PRAGMA setup at all.
- **Net effect: foreign key enforcement has been OFF for every single database operation in the app's entire runtime, for the whole time this project has existed** — except for the few milliseconds during the one-time startup connection. This predates this session entirely.
- **Concretely, this means every `ON DELETE CASCADE` declared anywhere in the schema has never actually fired.** Grepped the codebase: at least 12 places rely on this — `DeniDAO`, `HotelDAO`, `LaundryDAO`, `PayrollDAO`, `QuotationDAO`, `RestaurantDAO`, `SaccoDAO` (×2), `StockTakeDAO`, `WorkshopDAO` (×2), plus 3 in `DatabaseManager` itself. Deleting a quotation, a stock take, a SACCO merry-go-round group, etc. should cascade-delete their child rows (quotation items, stock take items, group members) — instead, every one of those child rows has been silently orphaned in the database, accumulating indefinitely, for the entire life of every installation of this app.

## Proof, not just a read-through

Wrote a standalone test (downloaded a real `sqlite-jdbc` jar, same method as the v11.7 network-layer verification) that creates a parent/child table pair with `ON DELETE CASCADE`, inserts one row of each, deletes the parent, and checks whether the child survived:
- **Without** the fix: child row remains after the parent delete — cascade did not fire. Confirmed.
- **With** the fix applied exactly as written below: child row is gone — cascade fired correctly. Confirmed.

## The fix

- `getLocalConnection()` now applies `PRAGMA foreign_keys = ON` and `PRAGMA busy_timeout = 5000` to every connection it returns, via a new `applyConnectionPragmas()` helper — not just the one used during `initialize()`.
- The `SHARED` network mode's connection path (introduced in v11.7) gets the same treatment, plus a longer `busy_timeout = 15000` specifically for that mode, since a genuinely network-shared file is slower and less predictable to contend for than local multi-threaded access on one machine.
- `busy_timeout` is a secondary, related fix: without it, SQLite immediately throws `SQLITE_BUSY` if a write lock can't be acquired instantly rather than retrying for a bounded time — a much more realistic failure mode now that multi-computer SERVER mode (v11.7) means several client sessions can genuinely write concurrently against the same local file on the host.

## What this doesn't retroactively fix

Any orphaned rows that already accumulated in an existing installation's database before this fix remain orphaned — this fix only ensures cascades fire correctly *going forward*. There's no cleanup migration for pre-existing orphans in this pass; that would need to be a separate, deliberate data-cleanup script if it turns out to matter for a real installation's data.
